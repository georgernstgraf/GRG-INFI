Die Datenbank hinter Facebook

Zehn Milliarden Lesevorgänge pro Sekunde — und die Frage, ob dort überhaupt noch gesperrt wird.

1. Die Einstiegsfrage

Du öffnest die App, scrollst eine Minute, tippst ein Herzchen. Aus deiner Sicht waren das drei Gesten.

Aus Sicht der Datenbank waren es hunderte Lesevorgänge: Beiträge, Autoren, Freundschaften, Zähler, Einstellungen, Sichtbarkeiten. Jeder Beitrag im Feed ist eine Abfrage, und ein Beitrag reicht selten.

Die Frage dieser Lektion Wie viele Datenbankzugriffe erzeugt ein einziger Nutzer pro Tag — und wie hält ein System das aus, ohne dass die Daten unbrauchbar werden?

Die Antwort hat zwei Teile: eine Zahl (Abschnitt 2) und einen Bauplan (Abschnitte 3–7). Der spannende Teil ist aber der dritte: Was passiert mit dem Sperren, das du aus KM5 kennst? Wird ein Datensatz, den Millionen gleichzeitig lesen, überhaupt noch gesperrt?

Die Antwort vorweg, weil sie überrascht: Es wurde nicht abgeschafft. Es wurde nachgerüstet, verkleinert und an den Rändern durch etwas anderes ersetzt. Warum das so ist, ist der Kern dieser Doppelstunde.

2. Das Zahlenbild — und eine Falle beim Lesen

Alle Zahlen unten stehen in wissenschaftlichen Papern, die Meta selbst veröffentlicht hat. Sie sind nicht geschätzt, sondern gemessen. Wichtig ist dabei weniger der Wert als das Jahr: Das System wächst, und eine Zahl ohne Jahr ist keine Angabe.

Aus der Sekundenzahl lässt sich die Tagesbilanz ausrechnen. Eine Stunde hat 3 600 Sekunden, ein Tag 86 400:

10 Milliarden/s × 86 400 s
  = 864 000 Milliarden
  = 864 Billionen Lesevorgänge pro Tag

20 Millionen/s × 86 400 s     -- Mittelwert
  = 1 728 000 Millionen
  = rund 1,7 Billionen Schreibvorgänge pro Tag

Verhältnis: genau 500 Lesevorgänge auf einen Schreibvorgang (864 Billionen geteilt durch 1,728 Billionen). Das ist der wichtigste Satz des ganzen Zahlenbilds — das System ist ein Lesesystem, in das gelegentlich geschrieben wird.

Und pro Kopf: 864 Billionen geteilt durch 3,6 Milliarden Nutzer ergibt rund 240 000 Lesevorgänge pro Nutzer und Tag, also knapp drei pro Sekunde, rund um die Uhr. Das ist die Antwort auf die Einstiegsfrage: Ein Scroll ist nicht eine Abfrage, sondern ein Vielfaches davon.

Achtung: die billion-Falle

Englische Paper schreiben billion für 10⁹ — das ist deutsch Milliarde. Deutsch Billion heißt englisch trillion und ist 10¹².

EnglischWertDeutsch
million10⁶Million
billion10⁹Milliarde
trillion10¹²Billion
quadrillion10¹⁵Billiarde

Ab „billion“ liegt der deutsche Name eine Sprosse tiefer. Wer „ten billion“ mit „zehn Billionen“ übersetzt, liegt um den Faktor 1000 daneben — und die ganze Stunde wäre falsch.

Der Fehler fällt dabei nicht auf: Beide Zahlen klingen groß und plausibel, nur eine ist um den Faktor 1000 falsch. Man sieht es dem Satz nicht an.

Genau diese Falle steckt auch in einer Zahl, die im Netz herumgeht: „TAO beantwortet eine Billiarde Anfragen pro Tag“. Im TAOBench-Paper steht das nicht. Dort steht „over ten billion reads per second“. Die Billiarde ist eine Rechnung (10 Milliarden × 86 400 ≈ 0,86 Billiarden), kein Zitat. Beides darf man verwenden — aber man muss wissen, welches von beidem man gerade sagt.

3. Der soziale Graph als zwei Tabellen

Bevor wir über Verteilung reden, müssen wir wissen, was da verteilt wird. Facebook speichert kein „Timeline-Objekt“. Es speichert einen Graphen: Knoten (Personen, Seiten, Fotos) und Kanten (Freundschaft, Like, Kommentar).

Im Datenmodell von TAO sind das zwei Tabellen — für den ganzen Graphen, mit Milliarden Zeilen:

CREATE TABLE objekt (                -- Knoten
  id     BIGINT PRIMARY KEY,         -- 4, 1000042, …
  typ    INT    NOT NULL,            -- Nutzer, Seite, Foto …
  daten  BLOB   NOT NULL             -- Felder serialisiert
);

CREATE TABLE assoziation (           -- Kanten
  id1    BIGINT NOT NULL,            -- Quellknoten
  typ    INT    NOT NULL,            -- FRIEND, LIKE …
  id2    BIGINT NOT NULL,            -- Zielknoten
  zeit   INT    NOT NULL,            -- 32-Bit-Zeitstempel
  PRIMARY KEY (id1, typ, id2)
);

Zwei Feinheiten lohnen einen Blick. Erstens liegen die Felder eines Knotens nicht in eigenen Spalten, sondern serialisiert in einer einzigen — es gibt kein `WHERE stadt = 'Graz'`, weil niemand danach sucht. Zweitens ist `zeit` Teil der Sortierung: Kanten liegen absteigend nach Zeit, die neuesten zuerst.

Damit wird „die letzten zwanzig Freunde von Anna“ zu einem Range-Scan über einen Präfix — nicht zu einem Join:

SELECT id2
FROM   assoziation
WHERE  id1 = 4 AND typ = 1          -- Annas Freundeskanten
ORDER  BY zeit DESC
LIMIT  20;
Merke Es gibt in diesem System keine Joins über Shards. Die API kennt nur Punktabfrage, Bereich und Zähler. Was in SQL ein `JOIN` wäre, löst die Anwendung durch mehrere gezielte Abfragen — oder es passiert gar nicht.

4. Sharding: warum Zusammenliegendes zusammenbleibt

Zehn Milliarden Lesevorgänge pro Sekunde passen auf keinen einzelnen Server. Die Daten werden deshalb geshardet: aufgeteilt in Stücke, die auf verschiedenen Maschinen liegen.

Die entscheidende Regel lautet: Ein Objekt gehört für immer zu genau einem Shard, und der Shard wird aus der `id` berechnet. Eine Kante liegt immer beim Quellknoten.

Shard = shard_von(id)

Beispiel:  objekt 4  (Anna)  → Shard 17
           objekt 9  (Bea)   → Shard 41

           Kante (4, FRIEND, 9)     liegt auf Shard 17   -- bei Anna
           Kante (9, FRIEND, 4)     liegt auf Shard 41   -- bei Bea

Das ist der Trick, der später das Locking klein hält: Fast alles, was eine Anfrage braucht, liegt auf einem Shard. Annas Freundesliste liegt bei Anna. Wer Annas Feed baut, muss nicht zwanzig Maschinen befragen, sondern eine.

Der Preis steht direkt daneben: Die Gegenkante liegt woanders. Eine Freundschaft sind zwei Zeilen auf zwei Shards, die zusammen stimmen müssen. Merke dir diesen Satz — er wird in Abschnitt 8 der Grund, warum es doch verteiltes Locking gibt.

Wer die Shards verwaltet, ist selbst ein System: der Shard Manager. Er kennt über eine Million Maschinen, verschiebt Shards bei Überlast und Failover und verwaltet bis zu Zehner Millionen Shards pro Anwendung.

5. MySQL bleibt im Kern — nur die Engine wechselt

Man erwartet hinter Facebook eine exotische Datenbank. Tatsächlich steht dort MySQL, und zwar in der Hauptdatenbank „UDB“ mit zig Petabytes. Was sich geändert hat, ist die Speicher-Engine darunter.

Über ein Jahrzehnt lang war das InnoDB: ein B-Baum. Jede Zeile liegt an einem berechneten Platz, Änderungen schreiben ganze Seiten neu. Bei Schreiblast auf Flash-Speicher wird das teuer — nicht weil Schreiben langsam wäre, sondern weil zu viel geschrieben wird. Dieses Verhältnis heißt Write-Amplification: wie viele Bytes das Laufwerk sieht, pro Byte Nutzdaten.

MyRocks ersetzt den B-Baum durch einen LSM-Baum (Log-Structured Merge Tree). Geschrieben wird zuerst in eine sortierte Datei im Speicher, die periodisch mit den bestehenden Dateien verschmolzen wird. Statt zufällig in Seiten zu schreiben, schreibt das Laufwerk große Blöcke hintereinander. Dieses Verschmelzen im Hintergrund kostet zusätzliche Schreibarbeit — der Preis für den Platzgewinn.

GrößeInnoDB (B-Baum)MyRocks (LSM-Baum)
PlatzbedarfReferenz40 bis 50 Prozent kleiner
Schreiblasthochetwa ein Zehntel
Lesen einer Zeileschnelllangsamer (mehr Ebenen)
SperrenZeilen und Lückennur Zeilen

Die letzte Zeile ist die wichtigste für heute. InnoDB sperrt nicht nur die Zeile, die geändert wird, sondern auch die Lücke davor (Gap-Lock). Damit verhindert es, dass während einer Transaktion jemand etwas „dazwischen“ einfügt — nötig für Eindeutigkeit über Präfixe und für statement-basierte Replikation.

MyRocks sperrt Zeilen, aber keine Lücken. Das ist weniger Wartezeit, aber auch weniger Garantie: Wer Eindeutigkeit über einen Präfix braucht, muss den vollen Primärschlüssel verwenden. Meta hat diese Einschränkung bewusst akzeptiert — der Platzgewinn war wichtiger.

6. TAO davor: die Schicht, die 96 Prozent abfängt

Wenn 500 Lesevorgänge auf einen Schreibvorgang kommen, ist die wichtigste Frage nicht „wie speichere ich schnell“, sondern „wie komme ich gar nicht bis zur Datenbank“.

TAO ist diese Schicht: ein Graph-Cache, der vor den MySQL-Datenbanken sitzt und in jeder Region läuft. Lesezugriffe gehen zuerst an TAO. Trifft TAO, war die Datenbank nie beteiligt — 2013 in 96,4 Prozent der Fälle.

TAO ist kein reiner Cache, sondern write-through: Ein Schreibvorgang geht an die Datenbank, und die Änderung wandert von dort zurück in die Caches. Der Rückweg ist der interessante Teil: TAO hängt seine Invalidierungs-Befehle in den Replikationsstrom von MySQL. Die Cache-Kopie erfährt von einer Änderung also auf demselben Weg, auf dem die Datenbank-Replikate sie erfahren.

Lesen:    App ──▶ TAO-Cache ──treffer──▶ App
                        └─kein Treffer─▶ MySQL ──▶ TAO füllt nach

Schreiben: App ──▶ MySQL ──Replikationsstrom──▶ TAO-Cache
                          (Invalidierung läuft mit)

Damit ist klar, warum das System lesend so schnell ist: Die teure Arbeit passiert im Speicher und in der Nähe der Nutzer, nicht auf der Festplatte.

7. ZippyDB: der zweite Speicher, mit Absicht anders

Neben TAO und der MySQL-Welt gibt es einen zweiten großen Speicher: ZippyDB, Metas größter stark konsistenter Schlüssel-Wert-Store. Er speichert Metadaten, Zähler, Konfiguration — Dinge, die sofort stimmen müssen.

Drei Bausteine reichen, um ihn zu verstehen:

Baustein 1 — Paxos statt „einer schreibt, alle hoffen“

Ein Shard hat eine Gruppe von Replikaten, die sich per Multi-Paxos auf eine Reihenfolge der Schreibvorgänge einigen. Zusätzlich gibt es asynchrone Mitläufer, die langsamer sein dürfen und billige Lesezugriffe in der eigenen Region erlauben.

Baustein 2 — Epoche und Leader-Lease

Schreibvorgänge müssen eine eindeutige Reihenfolge haben, sonst entsteht Unsinn. Dafür gibt es pro Shard eine Epoche mit genau einem Leader. Der Leader hält eine Lease: ein Zeitfenster, in dem nur er schreiben darf. Bleibt der Herzschlag aus, erhöht der Shard Manager die Epoche, und ein anderer übernimmt.

Das ist der erste wichtige Begriff für heute: Eine Lease ist keine Sperre. Sie fragt niemanden um Erlaubnis, sie gilt für eine Frist. Danach muss man neu bitten.

Baustein 3 — optimistische statt pessimistische Nebenläufigkeit

ZippyDB sperrt beim Lesen nichts. Der Client liest aus einem Schnappschuss, schickt Lese- und Schreibmenge an den Primary, und der prüft beim Commit, ob inzwischen jemand dieselben Schlüssel geändert hat. Kollision → Abbruch und neuer Versuch. Dieses Verfahren heißt optimistisches Concurrency Control (OCC) und ist pro Shard serialisierbar.

Ein einzelner physischer Shard fasst übrigens 50 bis 100 GB und enthält darin zehntausende sogenannte μShards (Mikro-Shards) — die kleine Einheit, die man verschieben kann, ohne die Anwendung zu ändern.

8. Wo Locking passiert — und ob es aufgegeben wurde

Jetzt zum Kern. Die ehrliche Antwort hat vier Etagen, und nur eine davon lautet „kein Locking“.

Etage 1 — im Shard: klassisches Locking, unverändert

Innerhalb einer MySQL-Instanz passiert genau das, was du aus KM5 kennst: Zeilen sperren, Transaktion, freigeben. Zwei Transaktionen, die dieselben Zeilen in verschiedener Reihenfolge sperren, laufen in einen Deadlock; die Datenbank bricht eine der beiden ab.

-- MySQL/PostgreSQL: Zeilen sperren, in fester Reihenfolge
BEGIN;
SELECT stand FROM konto WHERE id = 7  FOR UPDATE;   -- Sperre 7
SELECT stand FROM konto WHERE id = 12 FOR UPDATE;   -- dann 12
UPDATE konto SET stand = stand - 10 WHERE id = 7;
UPDATE konto SET stand = stand + 10 WHERE id = 12;
COMMIT;   -- erst jetzt fallen beide Sperren
Achtung: SQLite ist keine gute Demo dafür

SQLite kennt kein SELECT … FOR UPDATE. Es sperrt die ganze Datei: Eine zweite Schreibtransaktion bekommt database is locked, auch wenn sie eine völlig andere Zeile ändern will. Genau deshalb braucht es für dieses Kapitel MySQL oder PostgreSQL — und genau deshalb ist SQLite für ein Einzelplatz-Programm richtig und für einen Server falsch.

Etage 2 — über Shards hinweg: hier wurde Locking eingeführt

Und jetzt die Überraschung. Es wäre naheliegend, verteiltes Locking einfach wegzulassen. Meta hat das Gegenteil getan.

Zur Erinnerung aus Abschnitt 4: Eine Freundschaft sind zwei Kanten, und die Gegenkante liegt auf einem anderen Shard. Ältere Anwendungen behalfen sich mit eigenen Behelfslösungen — und die gingen schief, weil die Anwendung nicht wusste, ob ein Schreibvorgang fehlgeschlagen oder nur noch nicht repliziert war.

Deshalb hat TAO fehleratomare Transaktionen über Shards hinweg nachgerüstet. Sie funktionieren mit 2PC (Zwei-Phasen-Commit) und — entscheidend für deine Frage — mit 2PL (Zwei-Phasen-Sperren). Jede beteiligte Zeile wird gesperrt, bis alle Shards zugestimmt haben.

Transaktion: Anna und Bea werden Freunde

Phase 1 (prepare)
  Shard 17: Zeile (4, FRIEND, 9) sperren  → "ich kann"
  Shard 41: Zeile (9, FRIEND, 4) sperren  → "ich kann"

Phase 2 (commit)
  Koordinator: "commit"
  beide Shards schreiben endgültig, Sperren fallen

Stirbt ein Shard in Phase 1:
  alle brechen ab — nichts Halbes wird sichtbar

Diese Transaktionen sind opt-in: Man bezahlt sie nur, wenn man sie braucht. Aber man braucht sie oft — bidirektionale Beziehungen machen 52 Prozent aller Assoziationstypen aus. Verteiltes Locking ist hier also der Normalfall, nicht die Ausnahme.

Etage 3 — auf der Leseseite: wirklich kein Locking

Beim Lesen gibt es kein Sperren, und zwar mit Absicht. Zehn Milliarden Lesevorgänge pro Sekunde vertragen keine Wartezimmer.

Die Schwierigkeit ist nicht das Lesen selbst, sondern die Sichtbarkeit: Wenn eine Transaktion zwei Zeilen auf zwei Shards ändert, darf ein Leser nicht die eine neue und die andere alte Zeile sehen. Genau das garantiert RAMP (Read-Atomic Multi-Partition) auf Basis von Versionen: Der Leser bekommt eine atomare Momentaufnahme, ohne dass irgendjemand auf ihn wartet. Über 99,93 Prozent der Lesevorgänge brauchen dafür einen einzigen Netzwerk-Roundtrip; der Preis ist 0,42 Prozent mehr Speicher.

Wichtig ist, was das nicht ist: RAMP liefert atomare Sichtbarkeit, nicht Serialisierbarkeit. Man sieht entweder alles oder nichts — aber nicht notwendigerweise den „letzten“ Zustand.

Etage 4 — Führung und Cache: Leases statt Sperren

Wer darf schreiben? Diese Frage beantwortet kein Lock-Server, sondern eine Lease: In ZippyDB pro Epoche (Abschnitt 7), in TAO über einen eigenen Lease-Dienst (Skylease, beschrieben im Skybridge-Paper 2025). Leases sind der Grund, warum ein Failover funktioniert, ohne dass zwei Leader gleichzeitig schreiben.

Antwort auf die Einstiegsfrage Locking wurde nicht aufgegeben. Es wurde verkleinert (meist ein Shard), nachgerüstet (2PC + 2PL für die Gegenkante) und an den Rändern ersetzt: beim Lesen durch Versionen, bei der Führung durch Leases, bei Konflikten durch OCC.

9. Was man dafür aufgibt

Die Rechnung hat einen Preis, und der wird selten so offen ausgesprochen: Man gibt die globale Serialisierbarkeit auf. Es gibt keinen Zeitpunkt, zu dem „die ganze Welt“ denselben Stand sieht.

Stattdessen gilt Eventual Consistency: Replikate laufen hinterher. Im RAMP-TAO-Paper von 2021 steht die Zahl dafür — 99,99 Prozent der Replikate sind weniger als 60 Sekunden veraltet. Das klingt harmlos, bis man dazurechnet, dass in 60 Sekunden Milliarden Lesevorgänge passieren.

Seit 2025 gibt es dafür einen saubereren Begriff: bounded staleness — die Verzögerung ist nach oben begrenzt, und das System kann pro Lesevorgang nachweisen, ob der Stand aktuell genug ist (Skybridge). Man gibt also nicht „Korrektheit“ auf, sondern tauscht sie gegen eine zugesicherte Obergrenze.

Warum das praktisch funktioniert, zeigt eine Beobachtung aus TAOBench: Über 99 Prozent der heiß geschriebenen Schlüssel werden im Schnitt weniger als einmal pro Tag gelesen. Die Menge der heißen Schreiber und die Menge der heißen Leser überschneiden sich kaum. Man kann beide Seiten deshalb getrennt optimieren, ohne dass sie sich in die Quere kommen.

Welche Aussagen folgen aus „99,99 Prozent der Replikate sind weniger als 60 Sekunden veraltet“?
Warum ist es günstig, dass heiße Schreiber und heiße Leser kaum dieselben Schlüssel betreffen?

10. Messen statt glauben: TAOBench

Eine Frage bleibt: Woher weiß man, dass die Annahmen stimmen? Meta hat die eigene Last als Benchmark veröffentlicht — TAOBench (2022, Open Source). Er erzeugt Anfragen, die statistisch zur Produktion passen, inklusive der Schiefe: wenige Schlüssel werden sehr oft geschrieben, viele selten.

Interessant ist, wofür Meta den Benchmark selbst verwendet. Einer der vier genannten Anwendungsfälle lautet wörtlich: „assessing contention under longer lock hold times“ — den Streit um Sperren bewerten, wenn sie länger gehalten werden. Das Paper zeigt dazu eine Kurve: die Fehlerrate von Schreibtransaktionen über der zusätzlichen Zeit, die eine Sperre gehalten wird.

Damit ist die Ausgangsfrage beantwortet, und zwar mit einem unerwarteten Ergebnis: Locking ist bei Meta keine Altlast, die man loswerden will. Es ist eine Messgröße im Betrieb. Wer eine Sperre eine Millisekunde zu lange hält, sieht das in einer Kurve.

Der Benchmark vergleicht außerdem fünf verbreitete verteilte Datenbanken (Cloud Spanner, CockroachDB, PlanetScale, TiDB, YugabyteDB) — mit derselben Meta-Last. Das ist der praktische Nutzen: Man muss die eigene Datenbank nicht raten, man kann sie gegen eine echte Last stellen.

12. Typische Fehler

  • „billion heißt Billion.“ Es heißt Milliarde. Anti-Beispiel: „10 Billionen Lesevorgänge pro Sekunde“ — das wäre das Tausendfache und würde kein Rechenzentrum der Welt schaffen.
  • „NoSQL heißt ohne Sperren.“ ZippyDB ist streng konsistent und nutzt OCC; TAO sperrt über Shards mit 2PL. Anti-Beispiel: „Wir nehmen einen KV-Store, dann brauchen wir kein Transaktionsdesign.“
  • „Eine Lease ist eine Sperre.“ Eine Sperre gibt man frei, eine Lease läuft ab. Anti-Beispiel: „Der Leader hält die Sperre, bis er fertig ist“ — dann gibt es nach einem Absturz keinen neuen Leader.
  • „Sharding löst das Skalierungsproblem.“ Es verschiebt es: Die Gegenkante liegt woanders. Anti-Beispiel: „Wir sharden nach Nutzer-id, dann ist alles lokal“ — bis jemand beide Seiten einer Beziehung braucht.
  • „Eventual consistency heißt Datenverlust.“ Es heißt Verzögerung mit Schranke. Anti-Beispiel: „Der Beitrag ist weg“ — er ist nur noch nicht überall angekommen.
  • „Eine Zahl ohne Jahr ist eine Tatsache.“ Das System wächst; die Leserate hat sich zwischen 2013 und 2022 verzehnfacht. Anti-Beispiel: „TAO schafft eine Milliarde pro Sekunde“ — stimmte 2013, ist heute die Untergrenze.
