Blockchain als Datenbank

Eine Datenbank, in der niemand der Chef ist — und die deshalb jede Änderung verrät.

1. Die Einstiegsfrage

Jede Datenbank, die du bisher gebaut hast, hat einen unsichtbaren Gast: den Administrator. Diese Person darf UPDATE und DELETE ausführen — und niemand merkt es, wenn das Protokoll abgeschaltet ist.

Für ein Kassenbuch, ein Grundbuch oder die Lieferkette eines Medikaments ist genau das ein Problem. Nicht weil der Administrator böse ist, sondern weil jede Prüfung nur so viel wert ist wie die Instanz, die sie durchführt.

Die Frage dieser Lektion Wie müsste eine Datenbank aussehen, in der niemand heimlich eine Zeile ändern kann — auch nicht der Betreiber, auch nicht mit Datenbankzugriff?

2. Das Ziel: eine Kette, die sich selbst verrät

Am Ende der Doppelstunde steht ein Lauf, den du selbst starten kannst. Drei Blöcke, jeder mit Proof of Work, dann ein Sabotage-Versuch:

1) Drei Blöcke anlegen (Schwierigkeit 3 → 3 Hex-Nullen)

  Block 0: nonce= 9812 hash=000945c61142…  (1 Tx)
  Block 1: nonce=  856 hash=0001b6ac22ee…  (2 Tx)
  Block 2: nonce= 4791 hash=0006a0e5eaf3…  (3 Tx)

2) Prüfung der unveränderten Kette
   ok=true · Blöcke=3 · Fehler=0

3) Angriff: Betrag in Block 1 von 30 auf 9999 ändern
   ok=false
   · Block 1: merkle_root passt nicht zu den Transaktionen

4) Reparaturversuch: Block 1 neu minen
   ok=false
   · Block 2: prev_hash verweist nicht auf Block 1

Die Nonces und Hashes ändern sich bei jedem Lauf — die gefundene Zufallszahl hängt von der Uhrzeit ab. Die Struktur bleibt gleich: Ein geänderter Betrag bricht die Prüfung an zwei Stellen, und die zweite Stelle lässt sich nicht mitreparieren, ohne die ganze Kette neu zu rechnen.

3. Die Datenbank, die nur wächst

Datenbanktechnisch ist eine Blockchain zuerst eines: eine append-only Tabelle. Unser Beispielprojekt legt dafür zwei Tabellen an — mehr braucht die Kette nicht:

CREATE TABLE block (
  idx         INTEGER PRIMARY KEY,
  zeit        INTEGER NOT NULL,
  prev_hash   TEXT    NOT NULL,   -- Hash des Vorgängers
  merkle_root TEXT    NOT NULL,   -- Wurzel über alle Tx
  nonce       INTEGER NOT NULL,
  hash        TEXT    NOT NULL
);

CREATE TABLE tx (
  block_idx INTEGER NOT NULL REFERENCES block(idx),
  position  INTEGER NOT NULL,
  von       TEXT    NOT NULL,
  an        TEXT    NOT NULL,
  betrag    REAL    NOT NULL,
  PRIMARY KEY (block_idx, position)
);

Es gibt im Protokoll kein UPDATE und kein DELETE. Korrekturen laufen wie in der Buchhaltung: als Gegenbuchung. Ein falscher Betrag wird nicht überschrieben, sondern durch eine neue Transaktion ausgeglichen — beide bleiben sichtbar.

Daraus folgt der zweite Unterschied: Der Kontostand wird nicht gespeichert, sondern berechnet:

-- Saldo statt Kontostandsspalte:
SELECT sum(betrag) AS saldo
FROM   tx
WHERE  an = 'anna';
Merke Eine Blockchain speichert Ereignisse, keinen Zustand. Den Zustand (Saldo, Lagerstand, Grundbucheintrag) leitet jede Anwendung aus den Ereignissen ab — und kommt bei gleicher Kette immer zum selben Ergebnis.

Der dritte Unterschied ist der wichtigste: Es gibt keinen maßgeblichen Knoten. Jeder Teilnehmer hält eine vollständige Kopie und prüft jede neue Zeile selbst. Das ist keine Sicherung (Backup), sondern eine Replikation mit Prüfpflicht: Ein Backup ersetzt Daten, wenn sie verloren gehen; ein Replikat wird verworfen, wenn es nicht zur Kette passt.

4. Die Algorithmen: vier Bausteine, kein Zauber

Eine Blockchain ist aus vier bekannten Bausteinen zusammengesetzt. Wir gehen sie in der Reihenfolge durch, in der sie beim Bauen gebraucht werden.

Baustein 1 — Hashfunktion (SHA-256)

Ein Hash bildet beliebig viel Text auf 256 Bit ab. Drei Eigenschaften tragen die ganze Konstruktion:

  • deterministisch: gleicher Text, gleicher Hash — immer;
  • lawinenartig: ein geändertes Zeichen ändert etwa die Hälfte aller Bits;
  • einwegig: aus dem Hash lässt sich der Text nicht zurückrechnen.
sha256("abc")
// ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
// ein Zeichen anders → völlig anderer Hash, keine Ähnlichkeit

Baustein 2 — Merkle-Baum

Die Transaktionen eines Blocks landen nicht einzeln im Block-Hash. Sie werden zu einer Wurzel zusammengefasst: Benachbarte Hashes werden paarweise gehasht, die Ergebnisse wieder paarweise.

Das geht so weiter, bis eine einzige Wurzel übrig bleibt. Bei ungerader Anzahl wird das letzte Blatt mit sich selbst gepaart.

tx1 ─┐
     ├─ h(tx1+tx2) ─┐
tx2 ─┘              ├─ merkle_root
tx3 ─┐              │
     ├─ h(tx3+tx3) ─┘
tx3 ─┘  (ungerade → letztes doppelt)

Der Nutzen ist doppelt: Eine einzige geänderte Transaktion ändert die Wurzel — und ein Beweis, dass eine Transaktion in einem Block steckt, braucht nur log₂(n) Hashes. Bei 1024 Transaktionen sind das 10 statt 1024.

Baustein 3 — Proof of Work

Der Block-Hash entsteht aus Index, Zeit, Vorgänger-Hash, Merkle-Wurzel und einer frei wählbaren Zahl, der Nonce. Mining heißt: Nonce hochzählen, bis der Hash mit einer vereinbarten Anzahl Hex-Nullen beginnt.

// erwartete Versuche: 16^schwierigkeit
schwierigkeit 3 →      4.096 Versuche
schwierigkeit 4 →     65.536 Versuche
schwierigkeit 6 → 16.777.216 Versuche

Die Schwierigkeit ist kein Naturgesetz, sondern eine Absprache: Bitcoin passt sie alle 2016 Blöcke so an, dass im Schnitt alle zehn Minuten ein Block entsteht. Mehr Rechenleistung im Netz führt also nicht zu schnelleren Blöcken, sondern zu schwereren Aufgaben.

Achtung Proof of Work beweist keine Nützlichkeit. Er beweist nur, dass jemand Rechenzeit aufgewendet hat. Der „Wert“ entsteht daraus, dass ein Angreifer dieselbe Arbeit noch einmal leisten müsste.

Baustein 4 — Signaturen

Eine Transaktion wird mit dem privaten Schlüssel signiert und von jedem Knoten mit dem öffentlichen Schlüssel geprüft. Der private Schlüssel verlässt das Gerät nie; die Adresse ist im Wesentlichen ein Hash des öffentlichen Schlüssels.

Daraus folgt der bekannteste Merksatz der Branche: Not your keys, not your coins. Wer die Schlüssel verwahrt — eine Börse, eine Wallet-App, ein Backup — kann über die Coins verfügen. Die Kette prüft nur die Signatur, nicht die Absicht des Verwahrers.

5. Das verteilte System: Konsens statt Administrator

Ohne Administrator braucht die Kette eine Regel, welcher Stand gilt. Die einfachste Regel ist bis heute die von Bitcoin: Die längste Kette gewinnt — genauer: die Kette mit der meisten aufgewendeten Arbeit. Ein Knoten, der eine neue Kette sieht, vergleicht die Arbeit, nicht die Anzahl der Blöcke.

Neue Blöcke verbreiten sich über ein Peer-to-Peer-Netz: Jeder Knoten gibt sie an seine Nachbarn weiter (Gossip), ohne zentrale Anmeldung. Dabei entstehen zwangsläufig Forks: Zwei Miner finden fast gleichzeitig einen Block, ein Teil des Netzes hört zuerst von A, ein Teil von B.

Block 100 ─┬─ Block 101a ── Block 102a ── Block 103a   ← gewinnt
           └─ Block 101b   ← verwaist (orphan)

Der verlierende Block verschwindet nicht aus der Geschichte, er wird verwaist. Seine Transaktionen gelten als nicht bestätigt und wandern in den nächsten Block. Deshalb spricht man von Bestätigungen: Eine Transaktion ist umso sicherer, je mehr Blöcke danach gebaut wurden.

Merke Finalität ist bei Bitcoin wahrscheinlich, nicht absolut. Nach sechs Blöcken (im Schnitt eine Stunde) gilt eine Transaktion als praktisch unumkehrbar — nicht als mathematisch unumkehrbar.

Für die Verteidigung gegen Sybil-Angriffe ist das entscheidend: Identitäten sind gratis, ein Angreifer kann beliebig viele Knoten starten. Deshalb zählt nicht die Zahl der Knoten. Es zählt die Arbeit in der Kette (Proof of Work) oder das gebundene Kapital (Proof of Stake).

6. Was das bringt: die Vorteile

Der Nutzen ist nicht „Dezentralität“ als Selbstzweck, sondern die Prüfbarkeit ohne Treuhänder. Vier Vorteile halten einer nüchternen Prüfung stand:

VorteilWas er konkret bedeutet
IntegritätJede Änderung an alten Daten ist nachweisbar; niemand muss dem Betreiber glauben.
AuditierbarkeitDie vollständige Historie liegt bei jedem Teilnehmer; Prüfungen brauchen keinen Zugriff auf ein fremdes System.
ProvenienzHerkunft und Eigentümerwechsel sind lückenlos belegt — interessant für Lieferketten und Urkunden.
VerfügbarkeitEs gibt keinen einzelnen Ausfallpunkt; fällt ein Knoten aus, bleibt die Kette lesbar.

Dazu kommt die Programmierbarkeit: Smart Contracts sind Programme, die auf der Kette liegen und Bedingungen automatisch ausführen. Das ist ein echter Vorteil — und die Quelle der größten Schäden, wie wir später sehen.

Achtung Die Kette schützt nur, was auf ihr liegt. Ein Medikament, dessen Temperaturkurve ein Sensor liefert, ist nur so ehrlich wie der Sensor. Dieses Oracle-Problem ist der häufigste Denkfehler bei Blockchain-Projekten.

7. Was es kostet: Nachteile und Scheiterpunkte

Die Vorteile sind real, die Rechnung auch. Wer eine Blockchain vorschlägt, muss diese sechs Punkte beantworten können.

Energie

Proof of Work tauscht Strom gegen Sicherheit. Bitcoin verbraucht je nach Modell und Stichtag 138–190 TWh pro Jahr. Der Cambridge-Report von April 2025 nennt 138 TWh für das Jahr 2024, der Live-Schätzer liegt im November 2026 bei etwa 160 TWh.

Das ist die Größenordnung eines halben Prozents des Weltstromverbrauchs.

Proof of Stake braucht diese Rechnung nicht: Ethereum hat mit dem Merge am 15. September 2022 den Energieverbrauch um über 99,9 % gesenkt (Cambridge CCAF beziffert danach 7,87 GWh pro Jahr).

Der Vergleich mit einer relationalen Datenbank hinkt bewusst: SQLite hat keinen Konsens und kein Netzwerk. Genau diese beiden Posten sind der Preis — nicht die Speicherung.

Speicher und Governance

Jede Vollkopie trägt die gesamte Historie, und die wächst monoton. Wer Platz spart, schneidet alte Blöcke ab (Pruning) — und verliert damit einen Teil der Prüfbarkeit.

Governance ist der unterschätzte Punkt: Ein Protokoll ändert sich nur durch einen Hard Fork, und der wird von Menschen beschlossen. The DAO 2016 ist das Lehrstück — dazu gleich mehr.

Löschen und Schlüssel

Die DSGVO kennt ein Recht auf Löschung; eine Kette kennt kein DELETE. Personenbezogene Daten gehören deshalb nicht „zur Sicherheit“ on-chain. Und wer seinen privaten Schlüssel verliert, hat keinen Support: Es gibt kein Passwort-Zurücksetzen, nur den Verlust.

Zwei Gräber

TradeLens (Maersk/IBM) galt als Vorzeigeprojekt der Lieferkette. Im November 2022 wurde die Einstellung angekündigt, Ende des ersten Quartals 2023 war die Plattform offline. Begründung: Die „vollständige globale Zusammenarbeit der Branche“ sei nicht erreicht worden. Die Technik lief — das Ökosystem nicht.

ASX CHESS: Die Australische Börse wollte ihr Abwicklungssystem ab 2015 auf Blockchain umstellen. Im November 2022 wurde das Projekt nach rund sieben Jahren gestoppt; rund A$245–255 Mio. waren abgeschrieben. 2026 verglich sich die Börse mit der Aufsicht ASIC auf eine Strafe von A$20,5 Mio.

Achtung Beide Projekte scheiterten nicht an Hashes, sondern an Teilnehmerzahl, Rechtslage und Kosten. Wer eine Blockchain vorschlägt, muss zuerst diese drei Fragen beantworten.

8. Wie man es angreift

Angriffe auf eine Kette zielen selten auf die Hashfunktion. Sie zielen auf die Annahme, dass die Mehrheit ehrlich rechnet — oder auf die Software daneben.

Der 51-%-Angriff

Wer die Mehrheit der Rechenleistung hat, darf schneller Blöcke bauen als alle anderen zusammen. Damit kann er einen Block zurückrollen (Reorg) und eine bereits bestätigte Zahlung erneut ausgeben — Double Spending.

In der Praxis ist das kein Gedankenspiel. Ethereum Classic erlebte im August 2020 innerhalb von zwei Wochen drei Angriffe: Der erste rollte 3.693 Blöcke zurück und erbeutete 807.260 ETC (rund 5,6 Mio. USD), der dritte mehr als 7.000 Blöcke. Bitcoin Gold verlor im Mai 2018 rund 388.200 BTG (17,5–18 Mio. USD) über einen Reorg von 22 Blöcken.

Merke Der Angriff ist teuer, aber nicht unmöglich: Er lohnt sich, sobald die Beute größer ist als die Rechenzeit. Kleine Ketten mit wenig Hashrate sind deshalb besonders gefährdet.

Angriffe auf das Netz und auf Verträge

  • Sybil: viele billige Knoten — deshalb zählt Arbeit oder Stake, nicht Knotenzahl.
  • Eclipse: Ein Knoten wird vom Netz abgeschirmt und bekommt nur noch die Kette des Angreifers zu sehen.
  • Selfish Mining: Blöcke werden zurückgehalten und erst später veröffentlicht, um Konkurrenten Arbeit zu entwerten.
  • Smart-Contract-Fehler: The DAO 2016 verlor 3,6 Mio. ETH (rund 50–60 Mio. USD) durch eine ausnutzbare Funktion. Die Community reparierte per Hard Fork — die nicht geforkte Kette lebt als Ethereum Classic weiter.
  • Bridges: Der Vertrag, der Werte zwischen Ketten bewegt, verwahrt fremdes Geld — das beliebteste Ziel der letzten Jahre.

11. Typische Fehler

  • „Eine Blockchain ist unhackbar.“ Nicht die Kette wird gehackt, sondern die Umgebung: Börsen, Bridges, Schlüssel, Verträge. Anti-Beispiel: „Die Coins sind sicher, sie liegen auf der Börse.“
  • „On-Chain heißt wahr.“ Die Kette beweist, dass ein Eintrag unverändert ist — nicht, dass er stimmt. Anti-Beispiel: „Die Temperatur steht in der Chain, also war die Kühlkette intakt.“
  • „Dezentral heißt ohne Betreiber.“ Es gibt fast immer jemanden, der Software schreibt, Updates verteilt oder Schlüssel verwahrt. Anti-Beispiel: „Das Netz entscheidet selbst“ — bei einem Hard Fork entscheiden Menschen.
  • „Der Hash speichert die Daten.“ Er ist eine Prüfsumme. Anti-Beispiel: „Wir legen die Rechnungen in den Hash.“
  • „Ein Smart Contract ist ein Vertrag.“ Er ist Code ohne Gericht: Was er falsch macht, macht er unwiderruflich falsch. Anti-Beispiel: „Der Code führt schon aus, das klären wir später.“
  • „Blockchain löst das Löschproblem.“ Sie verschärft es: Was einmal drin ist, bleibt. Anti-Beispiel: personenbezogene Daten „sicherheitshalber“ on-chain speichern.
