Node.js + Prisma 7 — der ORM-Weg

Nach der Reparaturstunde vom 22.09.: Wir holen das ORM zurück — diesmal mit Node.js als Runtime für die Datenbank-Werkzeugkette und Prisma 7 mit SQLite.

Entscheidung (2026-09-29): Wir bleiben vorerst bei Prisma und wechseln für die DB-Werkzeugkette auf Node.js. Grund: Prisma 7 braucht zwingend einen nativen Driver Adapter. Unter Node ist das der Normalfall (better-sqlite3) — unter Deno war genau das die Reibung vom 22.09. Der allgemeine Unterrichts-Code bleibt Deno/TypeScript.

1. Ziel dieser Lesson

Am Ende hast du ein lauffähiges Prisma-7-Projekt: Node initialisiert, Prisma gepinnt, Schema geschrieben, migriert, geseedet — und dieselben fünf Diagnose-Queries aus UE 1 einmal über die Prisma-API gestellt. Du verstehst, was ein ORM dir abnimmt und wo es dich ausbremst.

2. Warum überhaupt Node?

Prisma 7 hat die frühere Rust-Query-Engine entfernt. Der Client redet nicht mehr selbst mit der Datenbank, sondern über einen Driver Adapter — für SQLite ist das better-sqlite3, ein natives Node-Modul. Unter Node läuft das ohne Sonderbehandlung; unter Deno musste man mit npm:-Specifiern und Berechtigungen hantieren.

Merksatz: Node ist hier Transportmittel für Prisma, nicht die neue Unterrichts-Runtime.

3. Projekt aufsetzen

Ein leeres Verzeichnis, dann Node initialisieren. Wir schreiben ESM ("type": "module"):

npm init -y
npm pkg set type=module

# Prisma 7 — BITTE pinnen!
npm i prisma@7 @prisma/client@7 @prisma/adapter-better-sqlite3@7 dotenv

# Node ≥ 22.6 blockt Install-Scripts standardmäßig:
npm approve-scripts --all

Das @7 ist kein Schönheitsfehler: npm i prisma ohne Version zieht derzeit die 8.0.0-RC — genau das Chaos vom 22.09.

4. Das Schema

Prisma beschreibt die Datenbank in einer eigenen Sprache. Datei: prisma/schema.prisma.

generator client {
  provider = "prisma-client-js"   // Import: @prisma/client
}

datasource db {
  provider = "sqlite"
}

model Label {
  id        Int         @id @default(autoincrement())
  name      String      @unique
  kuenstler Kuenstler[]
}

model Kuenstler {
  id      Int    @id @default(autoincrement())
  name    String
  labelId Int?                       // NULL erlaubt -> "ohne Label"
  label   Label? @relation(fields: [labelId], references: [id])
  songs   Song[]
}

model Song {
  id          Int       @id @default(autoincrement())
  titel       String
  dauerSek    Int
  kuenstlerId Int
  kuenstler   Kuenstler @relation(fields: [kuenstlerId], references: [id])
}

Anders als beim SQL-Handwerk stehen hier Beziehungen als Felder (songs, label) — daraus baut Prisma die Fremdschlüssel.

5. Verbindung & Migration

Die Verbindungs-URL steht in .env (nicht im Schema):

# .env
DATABASE_URL="file:./dev.db"

Die Prisma-CLI liest sie über prisma7.config.ts und legt beim Migrieren die SQL-Migration plus den Client an:

npx prisma migrate dev --name init
npx prisma generate      # passiert bei migrate dev automatisch

Ergebnis: prisma/migrations/…_init/migration.sql — echtes SQL, das du lesen kannst.

6. Den Client verbinden (Driver Adapter!)

Der wichtigste neue Baustein. Ohne Adapter startet der Client nicht:

// src/prisma.js
import { PrismaClient } from "@prisma/client";
import { PrismaBetterSqlite3 } from "@prisma/adapter-better-sqlite3";

const adapter = new PrismaBetterSqlite3({
  url: process.env.DATABASE_URL ?? "file:./dev.db",
});
export const prisma = new PrismaClient({ adapter });

Die fünfte Zeile ist die Lehrstunde: Prisma hat keinen Self-JOIN. Für solche Fälle gibt es den Fluchtweg $queryRaw — rohes SQL, typisiert zurückgegeben.

// Die Zähl-Variante aus Frage 4 — kurz und klar:

8. Typische Fehler

  • Ungepinntes Prisma: npm i prisma → 8.0.0-RC. Immer @7.
  • Adapter vergessen: new PrismaClient() ohne { adapter } bricht unter Prisma 7 ab.
  • Kein .env: Ohne DATABASE_URL findet die CLI die DB nicht.
  • Install-Scripts geblockt: better-sqlite3 bleibt ohne approve-scripts ungebaut.
  • having über _count._all: Prisma filtert über ein Feld: having: { kuenstlerId: { _count: { gte: 2 } } }.
